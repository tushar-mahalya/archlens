# ADR-001: Identify repeated submissions with a request key

**Status:** proposed.
**Deciders:** unknown.
**Date:** unknown.
**Evidence basis:** present-day analysis of a fictional implementation, not historical approval.

## Context

A caller can repeat a submission when it does not know the first result.
Creating another order could duplicate the caller's intent.

## Options

| Option | Benefit | Cost | Evaluation |
|---|---|---|---|
| Create a row for every call | Simple intake | Repeated calls create extra orders | Present-day comparison only |
| Enforce a unique request key | Repeated matching calls return one ID | Callers must manage keys | Implemented in the example |

## Proposal

Use the request key to identify one order.
Reject reuse with different data rather than silently accepting it.

## Consequences

The store enforces uniqueness. Callers need a stable key for each intended order.
The current key scope is the whole store, not a tenant.
The example does not expire keys or provide a retention policy.

## Reversal cost and review trigger

A replacement would change the public contract and the unique constraint.
Review the design before adding tenants or a policy that deletes request keys.
Define the expected duplicate behavior before that change.
